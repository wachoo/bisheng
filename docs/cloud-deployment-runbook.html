网络出入口清单

交付给客户运维时可整节作为放行依据。原则：入向只开 443（+80 用于证书），其余端口保持内网；出向按实际启用的功能逐项放行，未启用的功能对应域名可以不开。

离线 / 纯内网部署

  1. 镜像：docker/data/img 下的 12 个 .tar.gz（约 5.8GB）直接 docker load，无需访问 registry。
  2. 证书：使用内部 CA 或商业证书，可关闭 ACME 出向。
  3. 模型 / 解析：改为内网端点（vLLM、自建 MinerU、ETL4LM），并在系统配置里改 URL。
  4. 企微：完全不出网时企微 SSO 与组织同步不可用；必须使用则放行三个企微域名，或配置正向代理。
  5. 时间同步：使用内网 NTP。

最小放行清单：入向 443（+ 按需 80 与 office.<域名>），出向企微三个域名 + 实际使用的模型/解析域名；其余都是安装期依赖，可离线解决。

03镜像获取与构建

中间件

全部来自私有仓库，compose 会自动拉取，无需单独处理。

后端

标准构建的第一行是 FROM dataelement/bisheng-backend:base.v10。这个 base 镜像由 src/backend/base.Dockerfile 构建：CI 在推送 base.v* tag 时运行它，版本号取自 tag（base.v10 → :base.v10-amd64，再由 multi-arch manifest 合成最终 tag）。

层内容
基础python:3.11-slim
系统库gcc / build-essential、libreoffice、ffmpeg、wget、vim、中文字体、libgl
工具pandoc 3.6.4（GitHub release）、uv（astral.sh）
Pythonuv sync --frozen --no-dev 形成的 venv 快照
数据NLTK punkt / pos_tagger、playwright chromium 及系统依赖

它承担的是重量级、变化慢的部分，所以 Dockerfile 只需在其上补依赖差异和源码。自行构建 base 需要同时满足这些网络条件：

依赖来源
python:3.11-slimDocker Hub（通常最先失败）
apt 包Debian 源
pandocgithub.com/jgm/pandoc/releases
uvastral.sh
chromiumplaywright 下载站

Docker Hub 不可达的机器上，直接从 base.Dockerfile 构建会在拉取 python:3.11-slim 时失败。实测可行的路径分四步。

1 · 从镜像代理准备 python 基础镜像

docker pull docker.m.daocloud.io/library/python:3.11-slim
docker tag docker.m.daocloud.io/library/python:3.11-slim python:3.11-slim

2 · 生成加速版 Dockerfile（在 base.Dockerfile 的 FROM 之后插入，并把结果写成构建上下文内的 base.Dockerfile.fast。BuildKit 会把 -f 的裸文件名解析成上下文内相对路径，放 /tmp 会报 failed to read dockerfile: open /var/lib/docker/tmp/buildkit-mount…: no such file or directory）

cd src/backend
{ head -n1 base.Dockerfile
  cat <<'EOF'
RUN sed -i "s|deb.debian.org|mirrors.aliyun.com|g" /etc/apt/sources.list.d/debian.sources 2>/dev/null || \
    sed -i "s|deb.debian.org|mirrors.aliyun.com|g" /etc/apt/sources.list
ENV UV_DEFAULT_INDEX=https://mirrors.aliyun.com/pypi/simple
ENV UV_INDEX_URL=https://mirrors.aliyun.com/pypi/simple
ENV PLAYWRIGHT_DOWNLOAD_HOST=https://cdn.npmmirror.com/binaries/playwright
ENV UV_HTTP_TIMEOUT=300
EOF
  tail -n +2 base.Dockerfile; } > base.Dockerfile.fast

head -8 base.Dockerfile.fast        # 应看到 FROM 之后紧跟 RUN sed …

（base.Dockerfile.fast 已加入 .gitignore，不会污染工作区。）

UV_HTTP_TIMEOUT=300 是必须的：uv 默认 30s 超时，在约 0.8 MB/s 的经济型带宽上下载 rapidfuzz、playwright 这类几十 MB 的包会直接失败（实测报 Failed to download … network timeout）。

3 · 后台构建（断开 SSH 不影响）

cd src/backend
nohup sh -c 'docker build -f base.Dockerfile.fast --platform linux/amd64 \
  -t dataelement/bisheng-backend:base.v10 . > /tmp/base-build.log 2>&1; \
  echo "EXIT=$?" >> /tmp/base-build.log' >/dev/null 2>&1 &

tail -f /tmp/base-build.log
docker images | grep base.v10        # 成功才有输出

成功标志：BuildKit 日志出现 naming to docker.io/dataelement/bisheng-backend:base.v10，且末尾 EXIT=0；旧版 builder 的 Successfully tagged … 在 BuildKit 下不会出现。

完成后校验 NLTK 数据确实装进了基础镜像：

docker run --rm dataelement/bisheng-backend:base.v10 python -c \
  "import nltk; [nltk.data.find(p) for p in ('tokenizers/punkt','tokenizers/punkt_tab','taggers/averaged_perceptron_tagger','taggers/averaged_perceptron_tagger_eng')]; print('NLTK OK')"

4 · 用标准 Dockerfile 构建正式后端镜像

cd src/backend
docker build -t bisheng-backend:src-v3.0.1-<MMDD> .

实测耗时与资源

阶段耗时（4C / 14 GiB、约 5–6 Mbps）
apt 依赖（300+ 包，含 gcc / libreoffice）10–20 分钟
pandoc / uv sync / NLTK / chromium15–25 分钟
标准 Dockerfile 构建（依赖已缓存）5–10 分钟

构建前检查：磁盘预留 ≥ 10 GB（不足时先 docker builder prune -f、docker image prune -f，再用 df -h / 确认）；停掉 OnlyOffice 等非必要容器腾出 2–3 GB 内存；经济型实例出带宽约 5 Mbps（0.7–0.8 MB/s），临时提到 100 Mbps 可快十倍。

arm64 还需按 CI 的做法先删掉 ibm-db（该驱动不支持 arm64）。镜像代理可用时，直接 docker pull dataelement/bisheng-backend:base.v10 更省事。

拉不到 base.v10 时，只能用增量方式：

docker create --name tmp bisheng-backend:src-v3.0.1-<旧MMDD>
docker cp bisheng/.../xxx.py tmp:/app/bisheng/.../xxx.py
docker commit --change 'CMD ["sh", "entrypoint.sh"]' \
  tmp bisheng-backend:src-v3.0.1-<MMDD>
docker rm -f tmp

内容正确，但不可复现。基础镜像可用后应重新执行标准构建。

前端

在本机构建产物，传到服务器再打包镜像：

# 本机
cd src/frontend
pnpm install --frozen-lockfile
pnpm --filter bisheng build       # platform
pnpm --filter bishengchat build   # client
tar czf /tmp/fe-build.tgz client/build platform/build
scp /tmp/fe-build.tgz root@<host>:/tmp/
# 服务器
mkdir -p /tmp/fe-release && tar xzf /tmp/fe-build.tgz -C /tmp/fe-release
cat > /tmp/fe-release/Dockerfile <<'EOF'
FROM bisheng-frontend:src-v3.0.1-<旧MMDD>
RUN rm -rf /usr/share/nginx/html/platform /usr/share/nginx/html/client

先删后拷。不清理旧目录，历史构建的 chunk 会残留在镜像里，浏览器可能加载到旧资源。

服务器本机构建

也可以在这台机器上直接构建，不依赖本机产物。Dockerfile 最后一段是 FROM nginx（未固定版本），Docker Hub 不可达时要先给本地 nginx 打 latest 标签：

docker pull docker.m.daocloud.io/library/node:20-alpine
docker tag  docker.m.daocloud.io/library/node:20-alpine node:20-alpine
docker tag  docker.m.daocloud.io/library/nginx:1.30-alpine nginx:latest

cd src/frontend
docker build -f Dockerfile -t bisheng-frontend:src-v3.0.2-<MMDD> .

不预先给 nginx 打标签会报 nginx: failed to do request … i/o timeout。npm 依赖走 src/frontend/.npmrc 的 registry.npmmirror.com，1900+ 包，约 15–20 分钟；产物镜像约 140 MB。

05域名与 TLS

只接受域名访问

tls-proxy 里加两个 default server：IP 直连在 TLS 握手阶段被拒，80 直接断连。

server { listen 80 default_server;          server_name _; return 444; }
server { listen 443 ssl default_server;     server_name _; ssl_reject_handshake on; }

证书

用 acme.sh 申请 Let's Encrypt。域名未备案时 80 会被入口拦截，只能走 TLS-ALPN-01：

/root/.acme.sh/acme.sh --issue --alpn -d <域名> --server letsencrypt \
  --pre-hook  "docker stop bisheng-tls-proxy" \
  --post-hook "/usr/local/sbin/bisheng-tls-reload.sh" \
  --accountemail admin@<域名>

备案完成后改用 webroot，续期不再中断服务：

/root/.acme.sh/acme.sh --issue -d <域名> --webroot /var/www/acme --server letsencrypt

配套两处：compose 挂载 /var/www/acme 只读进 tls-proxy；80 的 server 里加

location ^~ /.well-known/acme-challenge/ {
    root /var/www/acme;
    default_type text/plain;
}

安装与续期

/root/.acme.sh/acme.sh --install-cert -d <域名> --ecc \
  --key-file       /etc/nginx/ssl/server.key \
  --fullchain-file /etc/nginx/ssl/server.crt \
  --reloadcmd      /usr/local/sbin/bisheng-tls-reload.sh

bisheng-tls-reload.sh 先确保容器已启动、nginx -t 通过，再 reload——ALPN 续期会停容器，不兜底就会 reload 失败。

中断窗口：TLS-ALPN 需独占 443，续期时站点中断 10–20 秒；HTTP-01 无中断。cron 由 acme.sh 安装，每天检查 4 次。

07MinIO

三个身份分开用，root 只留给管理台：

身份使用方权限范围
root管理台全部
bisheng-appbackend / worker / beatbisheng + tmp-dir
bisheng-milvusmilvusa-bucket

策略必须包含 lifecycle：s3:GetLifecycleConfiguration、s3:PutLifecycleConfiguration。缺了它 backend 启动时 _ensure_tmp_bucket_lifecycle 会 AccessDenied，容器反复重启。MinIO 只认 AWS 风格 action 名，且没有 DeleteLifecycleConfiguration。

管理台

容器带 --console-address :9001，但默认只映射了 9100:9000。需要时加映射，建议只绑回环：

- "9100:9000"
- "127.0.0.1:9001:9001"

ssh -N -L 9001:127.0.0.1:9001 root@<host>   # 然后开 http://127.0.0.1:9001

要公网开放，先在安全组限制来源 IP，并换掉默认口令——管理台是覆盖全部存储文件的完整界面。

08OnlyOffice

不要用 7.1.1。它内置 Erlang OTP 22，在 cgroup v2 内核上 erl_child_setup 自旋 100% CPU，RabbitMQ 永远起不来。用 8.1.3 及以上。

ONLYOFFICE_IMAGE=docker.m.daocloud.io/onlyoffice/documentserver:8.1.3

必须给容器更大的 /dev/shm，默认 64 MB 会让编辑器卡死：

services:
  office:
    shm_size: "1gb"
    ports: ["8701:80"]
curl -s http://127.0.0.1:8701/healthcheck                       # true
curl -sI http://127.0.0.1:8701/web-apps/apps/api/documents/api.js  # 200

首次启动约 9 分钟（生成字体缓存）。平台通过 DB 配置 office_url 下发给前端，必须是 HTTPS，否则浏览器按混合内容拦截。推荐给一个子域名，把 SAN 追加进现有证书后反代到 office:80。

09安全加固

SSH 来源白名单

iptables 只放行运维网段和 Workbench 网段，其余到 22 的包直接 DROP，3389 一律丢弃：

ALLOW="<运维出口网段> 100.104.0.0/16"

脚本先删除本单元所有规则再重建，换白名单不会留孤儿规则；由 systemd 单元保证开机恢复。

端口最小化

  • frontend 的 3001 只绑 127.0.0.1，对外只走 443
  • 安全组只留 22 / 80 / 443，调试端口用完即关

凭据

  • .env 权限 600，不入库，历史备份定期清理
  • MinIO 服务 key 与 root 分离，轮换只换服务 key

10日常运维

更新镜像

# 改代码并提交 → 构建新镜像 → 改 .env 的 tag
docker compose up -d backend backend_worker backend_beat
docker compose exec frontend nginx -s reload   # 重建 backend 后刷新 upstream 解析

顺序不能反。backend 重建后容器 IP 会变，frontend 的 nginx 在启动时已把 backend:7860 解析成旧 IP，所有 /api 请求 502（容器内直连 127.0.0.1:7860 却是 200）。docker compose exec frontend nginx -s reload 让它重新解析即可；重建 frontend 容器也有效，但没必要。

更新前端镜像时方向反过来（frontend → TLS 反代）：

docker compose up -d frontend
cd nginx/tls && docker compose exec -T tls-proxy nginx -s reload

TLS 反代里是静态的 proxy_pass http://frontend:3001;，frontend 重建后 IP 变化，不 reload 就是全站 502。

11故障排查
