# 公司看板业务入口验收

这组任务用于检查业务发生后能否在看板查到相应结果。样本保留在本地 BiSheng 的 2026 年 11 月，管理端和工作台使用同一套本地数据库。台账、资产、对话、评价和处置均从产品接口进入；核对使用看板接口、运行明细和浏览器页面。

## 组织、专题与场景

| 对象 | 可操作的测试数据 |
| --- | --- |
| 普通用户 | 集中采购中心的 `board1126buyer`、财务共享中心的 `board1126finance`、运营管理中心的 `board1126ops`。三个账号各有一个主部门 |
| 采购协同 | 「采集验收1126·采购比价」由集中采购中心承建、运营管理中心支持，11 月 26 日投产。关联采购报价助手、问答库、报价 MCP 和复核 Skill |
| 工程履约 | 「采集验收1126·履约核对」由财务共享中心承建、运营管理中心支持，已计划、尚未投产。关联履约核查助手，也关联采购报价助手 |
| 代表案例 | 采购协同选择采购报价助手，工程履约选择履约核查助手。工作台使用门户可找到授权给普通账号的两位助手 |

## 台账与资产逐步对账

| 任务与业务入口 | 执行前预期 | 实际响应 |
| --- | --- | --- |

| 填 11 月科研经营月报和 1 条课题 | 报告显示科研项目 3、其中 AI 项目 2、在研 AI 项目 1；价值两项 2 和 1 万元 | 领导端读回上述数值，1 条课题；预算 24 万元，等效工作量 3 人天 |

| 通过 MCP 协议发现报价服务，创建公共报价复核 Skill | 工具目录 +1，Skill 目录 +1，未使用时不应产生调用量 | 工具 39→40，Skill 4→5。采购助手配置可回查到该库、工具和 Skill |
| 分别创建并正式上线两个助手 | 草稿不贡献数字员工存量或建成数；每次上线各 +1 | 两次草稿均保持原值；上线后目录数、年度建成数均依次为 0→1→2 |
| 场景管理手动关联资产，再为专题选择代表案例 | 采购场景有 4 个资产、履约场景有 2 个；共用助手仍只有一个资产。单纯关联不会产生使用量 | 读回 4 和 2 条关联，两个场景均可下钻；首次关联后公司服务量为 0 次、0 人，代表案例按各自专题回显 |

五项测试资产均由管理员创建。部门贡献榜按首发归属显示「临时访客」。三位普通用户所在部门用于验证实际使用归属，不作为这五项资产的贡献部门。资产步骤的原始数据包含每个动作前后的目录数、年度建成数和知识分类完成数。重复执行资产脚本会复用同名验收资产。[资产操作及配置](acceptance/live-assets.md) · [9 步实测增量](acceptance/live-assets.sample.json)

## 工作台对话、评价和处置

操作前分别预估数字员工终态、场景使用次数、去重人数和子事件的增量。工作台的日常对话使用基础模型，应用对话使用已上线的数字员工。两种入口各发出实际请求。

| 任务 | 预期 | 实测与判定 |
| --- | --- | --- |
| 采购人员在工作台日常对话调用火山方舟 | 收到回复，员工执行和场景服务量均 +0 | 收到终态消息 2。场景仍为 0 次、0 人 |
| 采购人员首次使用采购报价助手，要求查规则、加载 Skill、查报价 | 公司场景合计 1 次、1 人。正常报价应含 Q-1126，知识回答依据应含 K-1126 | 服务量、人数正确。实际模型调用 Skill 1 次、知识 2 次、MCP 1 次，报价回执含 Q-1126，知识片段没有答案。此轮助手实际用了默认模型 1，未采用原先为它配置的测试模型 3 |
| 财务人员使用采购助手，要求测试供方拒绝报价 | 2 次、2 人；Skill、知识调用和 MCP 失败数各 +1。若助手处理了异常并完成回复，员工终态仍计成功 | 消息 27 返回，运行归属财务共享中心。三项增量符合预期，工具返回错误标记和拒绝原因。监控可单独查看失败工具；知识片段仍缺答案 |
| 同一采购人员再次使用同一助手，测试供方正常报价 | 3 次、仍为 2 人；Skill、知识、MCP 成功各 +1，并取到报价与问答依据 | 次数和人数正确，三项调用增量正确，报价有 Q-1126，知识答案仍缺。此轮和上一轮已使用专用回放模型 |
| 运营人员使用履约核查助手 | 公司 4 次、3 人，归属运营管理中心，不增加知识和报价工具调用 | 使用火山方舟得到正常回复，终态消息 42；各项符合预期。采购、财务、运营三个部门分别记录 2、1、1 次成功运行 |
| 运营人员点赞消息 42；财务人员给消息 27 点踩并留言 | 回读两个消息分别为赞和踩；负反馈问题从 0 到 1，待处置 +1 | 两条消息评价值分别为 1 和 2，待处置 1。四次成功运行关联的回复中有一笔负评，按看板现行口径好评率为 75% |
| 管理员在监控端登记处理措施 | 原问题转入已处理，待处理 −1、已处理 +1，评价、历史任务和使用人数保持原值 | 提交后首次立即查询仍是 1 条待处理，随后同一问题可在已处理中回查，最终 0 条待处理、1 条已处理，好评率仍为 75% |

重启后从领导看板读回 4 次成功任务、3 名服务用户、4 次知识检索、3 次 Skill 调用、2 次成功和 1 次失败的 MCP 调用；从已处理列表按运行号查到原问题及措施。两位助手在场景明细中分别显示 3 次/2 人和 1 次/1 人。[战略进展截图](screenshots/parity/live-strategy.png) · [运营监控截图](screenshots/parity/live-monitor.png)

**检索质量。** 用原始问题和改写问题分别检索 Milvus 和 Elasticsearch，四次都命中同一条问答记录，其元数据中包含正确答案。正式助手构造引用片段时使用了只含问题的正文，答案留在元数据，未传给模型。因此监控中的“知识检索成功”可用于判断执行是否正常，还需要核对召回内容才能判断用户是否得到依据。[问答检索与引用复验](acceptance/live-qa-retrieval.py)

**模型选择。** 助手保存的模型 ID 仍需在系统助手可选模型清单中。初次执行时，测试模型 3 尚未加入清单，助手实际回退到默认模型 1，知识检索发生两次。将 3 加为非默认选项后，回放模型负责决定调用顺序，实际检索、MCP、Skill、消息存储、指标采集和汇总仍由产品执行。报价服务的正常返回和异常返回均使用本地测试供方。工作台日常对话、采购助手首轮和履约助手对话使用真实火山方舟模型。

## 本地环境与业务复跑

真实对话的供方为原配置的火山方舟模型 `deepseek-v4-flash`。本地后端原只连接内部 Docker 网络，检测在解析 `ark.cn-beijing.volces.com` 时失败。同一组配置从主机发起对话得到有效回复。当前本地 Compose 保留只通往该域名 443 的 TLS 转发，后端和 worker 仍在内部网络。系统模型检测通过，最终重启后仍显示正常。

将 `BOARD_SESSION` 指向本地管理员的 Playwright 登录状态。从仓库根目录启动本地工具回放模型，或对已存在的同名容器使用 `docker start board1126-test-model`。模型管理注册脚本会输出新环境的模型 ID，在创建采购助手时使用该值。

```powershell
$acceptance = 'features/v3.0.2/122-company-boards/acceptance'
$mock = (Resolve-Path (Join-Path $acceptance 'live-chat-model.py')).Path
docker run -d --name board1126-test-model --restart unless-stopped --network bisheng-dev_default --mount "type=bind,source=$mock,target=/model.py,readonly" python:3-alpine python -B /model.py
$env:BOARD_ADMIN_SESSION = $env:BOARD_SESSION
node (Join-Path $acceptance 'live-chat-provider.cjs')
```

1. 进入本项目的本地开发环境，在管理端以测试管理员登录，将 Playwright 登录状态放在仓库外。将 `BOARD_SESSION` 指向该文件，为测试账号创建步骤提供本地 `BOARD_TEST_PASS`。脚本使用本机 3001 端口。在已安装 Node.js、Playwright 和 Chrome 的环境运行。
2. 在当前特性目录的 `acceptance` 下运行 `node live-members.cjs` 和 `node live-planning.cjs seed`。台账脚本只在年度场景目标为空时填写目标，只在空白月份新建科研经营快照。在已有业务报表的环境，使用已归档的对账数据核对本次快照。
3. 按资产操作说明启动本地测试供方并创建资产。给三位测试人员授予验收资产的使用权限。用资产脚本输出的实际键执行下面的场景关联。采购助手同时选入两个场景，专用于验证跨场景去重。
4. 使用普通账号发起日常和助手对话，使用发起对话的账号评价；由有处置权限的账号处理评价。对话、评价和处置的命令与样本见[对话验收](acceptance/live-chat.md)。再次发起对话会产生新的真实记录，应核对当次增量。
5. 运行 `node live-boards.cjs`。该步骤打开四个看板视图，核对战略页使用次数、人数、投产场景、知识接入数和员工下钻。设置 `BOARD_EVIDENCE_DIR` 可导出当次战略与监控页面截图。

```powershell
# 在 acceptance 目录执行，BOARD_ASSET_MANIFEST 使用资产脚本的实际输出文件。
$a = Get-Content -Raw $env:BOARD_ASSET_MANIFEST | ConvertFrom-Json
$buyer = 'assistant:' + $a.employees[0]
$finance = 'assistant:' + $a.employees[1]
node live-planning.cjs link "$buyer,knowledge:$($a.knowledge),skill:$($a.skill),tool:$($a.tool)" "$finance,$buyer"
```
